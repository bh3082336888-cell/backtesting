# Stop and target path on trade charts: implementation plan

Follow-up to PR #8 (trade charts). Branch `feat/stop-path`, stacked on `feat/trade-charts`.

## Why

Trade records keep only the initial stop (`stop_init`) and initial target (`target`). On the real
runs, 89–95% of donchian_atr stop exits and 75–86% of bb_vwap_reversion target exits land away from
those initial levels, because the stop trails and the target follows VWAP. The chart therefore draws a
dotted line the exit never touches. This plan records every level the position actually carried and
draws it as a step line.

## Global Constraints

1. **The engine's numbers must not change.** Recording levels is observation only: equity, in-position
   flags, every existing trade field, recorded signals and rejection counts stay bit-identical. The
   whole existing suite (except the known environment failures below) must still pass unchanged.
2. **Three new trade fields, same name and meaning everywhere a trade record is built** (the backtest
   engine `perp_lab/engine/backtest.py::run_backtest` and the paper book
   `perp_lab/paper/runner.py::PaperBook`):
   - `level_time`: list of int, epoch ms. The time from which each level is in force.
   - `level_stop`: list of float. The stop in force from that time.
   - `level_target`: list of float. The target in force from that time; NaN means no target.
   - All three have the same length. Element 0 is at entry: `level_time[0] == entry_time`, with
     `stop_init` and the initial target (NaN if none). One more element is appended each time the stop
     or the target in force changes; nothing is appended when a hold signal leaves both unchanged (a
     non-ratcheting stop is ignored by the engine, so it is not a change). Engine: a change decided at
     the close of bar i takes effect from the open of bar i+1, so it is stamped `T[i+1]` (step 7 runs
     only for `i < last`, so `T[i+1]` exists). Paper: stamped at the decided bar's close,
     `open_time + TF_MS[tf]`.
3. **Levels come from the trusted engine and the paper book only.** No change to the sandbox
   protocol, decision logs, or anything a plugin sends.
4. **Old runs keep working.** Trade files without the three fields (every run made before this
   change) are charted exactly as today: horizontal initial lines labelled "initial stop" and
   "initial target". `pd.read_parquet` returns list columns as numpy arrays; chart code must accept
   arrays, lists, or a missing/None value per row.
5. Environment: run tests from your worktree with `/home/burhan/backtesting/.venv/bin/python -m pytest -p no:cacheprovider`.
   Use `-m "not sandbox"` for the full run. Real-sandbox tests can't confine a worker started from a
   second worktree (the venv's editable install points `perp_lab` at the main checkout), so they are
   not evidence either way. Never run anything in `/home/burhan/backtesting` (another session works
   there) and never read data files dated 2026-07 or later.
6. Commits: conventional subject (`feat(engine): ...`), prose body, one concern per commit, ending with

## Task 1: Record the level path in the engine and the paper book

Files: `perp_lab/engine/backtest.py`, `perp_lab/paper/runner.py`, tests in `tests/test_engine_costs.py`
(engine) and `tests/test_paper.py` (paper), or new focused test files beside them if those are crowded.

Engine (`run_backtest`):
- Keep three per-position lists. At the entry fill (step 4) set them to `[int(T[i])]`, `[stop]`,
  `[target]` (target is NaN when the signal had none).
- In step 7's hold branch, after the existing ratchet and target update, append
  `(int(T[i + 1]), stop, target)` if the stop or the target in force differs from the last recorded
  element (NaN equals NaN for this comparison).
- `close_pos` writes copies of the three lists into the trade dict as `level_time`, `level_stop`,
  `level_target`.
- Change nothing else: no reordering of steps, no new branches in the fill logic.
- If an existing test pins the exact set of trade columns or keys, extend it with the three fields.
  That is the only change to an existing test this task may make.

Paper book (`PaperBook`):
- `_open` starts the three lists in the position dict: `[ts]`, `[sig.stop]`, `[target_init]`.
- `on_closed_bar`'s hold branch appends `(int(bars.open_time.iloc[-1]) + TF_MS[self.tf], p["stop"], p["target"])`
  when the stop or target in force changed.
- `_close` writes the three fields into the trade dict.

Tests (write them first and watch them fail):
- Engine, with the `Scripted` helper in `tests/conftest.py` on `flat_bars`-style bars (prices chosen
  so nothing stops out early). Enter long with stop S0 and no target. Then: a hold that ratchets the
  stop up, a hold with a lower stop (ignored, so no new element), a hold that sets a target, and a
  hold that repeats the same stop and target (no new element). Exit. Assert the exact three lists,
  including that each time is the open of the bar after the decision, and that `level_time[0] == entry_time`.
- Engine: a trade whose stop and target never change has one-element lists equal to
  `[entry_time]`, `[stop_init]`, `[target]`.
- Engine, a short position: the ratchet direction is mirrored and recorded.
- Round trip: a trades frame with the three list columns written with `perp_lab.runs.write_run`
  and read back with `pd.read_parquet` keeps the values (they come back as arrays).
- Paper: drive a `PaperBook` through entry, a stop raise on a closed bar, and a stop-out on a quote
  (follow the existing patterns in `tests/test_paper.py`), and assert its trade's three lists.

## Task 2: Draw the level path on the chart, and document it

Files: `dashboard/trade_chart.py`, `dashboard/app.py` (caption only), `tests/test_trade_chart.py`,
`README.md`. Two commits: the chart change with its tests, then the README.

- Stop and target lines become step lines that follow the recorded levels: from `level_time[k]` the
  line sits at `level_stop[k]` until `level_time[k+1]` (or the exit time for the last element), then
  steps to the next value. Build each as one trace with `None` breaks between trades, as
  `_segments` does now. A NaN target ends the target line until a later non-NaN element starts it
  again.
- A row without levels (missing column, None, or empty) draws today's horizontal initial line.
- Legend names: "stop" and "target" when any charted row has levels; otherwise keep
  "initial stop" and "initial target".
- Hover: when the row has levels, add `stop at exit <price>` and `target at exit <price or —>`
  (the last element's values).
- `dashboard/app.py`: the caption says "dotted: stop (red) and target (blue), as they moved" when
  levels are present, and keeps the current wording otherwise. Pass the information down however
  is simplest (for example a helper in `trade_chart.py` that says whether a frame has levels).
- README: in the trade-charts bullets, replace "Only the initial stop and target are logged, so a
  trailing stop or a moved target exits off its dotted line." with a sentence saying runs record each
  stop and target change (`level_time`, `level_stop`, `level_target`) and the chart draws them as
  step lines, while runs made before this change show only the initial levels.
- Tests: a trade with a trailing stop (three levels) produces exactly the expected step vertices;
  a target that goes NaN then returns breaks and resumes; a frame read back from parquet (array
  values) works; old-format trades still give the "initial stop" / "initial target" traces unchanged;
  hover text includes the at-exit values; the dashboard page (AppTest, as in the existing tests)
  shows the "as they moved" caption for a run whose trades have levels.
